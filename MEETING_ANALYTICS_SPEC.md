# Дополнительное ТЗ: «Аналитика встреч»

Проект: «Задачи и встречи». Дата: 13 ноября 2026 года.

## 1. Цель и границы доработки

Расширить существующее локальное приложение разделами «Входящие записи» и «Аналитика встреч». Пользователь загружает короткое видео либо помещает его в настроенную локальную папку. Приложение автоматически извлекает аудио, распознаёт речь, анализирует фактическое содержание и сохраняет структурированные итоги. Отдельное нажатие «Создать конспект» или «Сформировать итоги» для нового видео не требуется.

Реализовать доработку в текущем проекте: FastAPI, SQLite, русскоязычный интерфейс на HTML/CSS/JavaScript без сборки. Сохранить существующие сценарии проектов, аудио, TXT, вставленного текста и личных задач.

Анализируется речь из звуковой дорожки. Распознавание изображений, слайдов, лиц, эмоций и текста на экране в эту доработку не входит. Пример встречи с клиентом из исходного запроса иллюстрирует оформление; его нельзя использовать как результат обработки.

## 2. Существующие механизмы, которые необходимо использовать

- `meeting_app/main.py`: авторизация, проверка владельца, создание и просмотр встреч, сохранение итогов и личных задач. Сейчас обработка аудио состоит из двух ручных запросов.
- `meeting_app/ai.py`: единственная граница вызовов OpenAI; функции `transcribe`, `analyze`, схема `Results`, проверки явных личных поручений.
- `meeting_app/db.py`: SQLite и миграции через `PRAGMA user_version`. На момент подготовки ТЗ реализована версия 1; её менять запрещено.
- `meeting_app/static/app.js`, `style.css`, `index.html`: интерфейс и навигация.
- `backup.py`: резервное копирование базы, оригинального аудио и защищённого ключа.

Текущая схема `Results` уже содержит `summary`, `topics`, `decisions`, `tasks`, `open_questions`, а также `agreements`, `risks`, `next_steps`. Не создавать параллельную несовместимую схему результатов. Новые фоновые задания должны использовать общую логику анализа и сохранения, а не вызывать собственные HTTP-маршруты.

## 3. Раздел «Входящие записи»

### 3.1. Загрузка через интерфейс

Добавить пункт навигации «Входящие записи». На странице разместить область перетаскивания и кнопку выбора файла, список записей и форму метаданных:

- проект из проектов текущего пользователя — обязателен;
- название встречи — по умолчанию имя файла без расширения, доступно редактирование;
- дата и время записи — по умолчанию момент загрузки, доступно редактирование;
- один или несколько файлов WebM/MP4, каждый создаёт отдельную встречу.

При пакетной загрузке проект и дата из формы применяются ко всем выбранным файлам; название по умолчанию берётся отдельно из каждого имени. Результат приёма и ошибки показывать для каждого файла независимо.

Установить следующие ограничения новой загрузки:

- контейнер WebM или MP4 с видеопотоком и доступной звуковой дорожкой;
- длительность от 120 до 300 секунд включительно;
- размер не более 200 МиБ на файл, лимит проверять потоково на сервере;
- проверять фактический контейнер, потоки, длительность и возможность декодирования. Расширение и MIME из браузера недостаточны;
- повреждённое видео, файл без звука, неподдерживаемый кодек и несоответствие формата отклонять с понятным объяснением.

Новый диапазон длительности применяется только к видео. Существующие правила аудиозагрузки до пяти минут сохраняются.

Показывать прогресс передачи файла в процентах. После приёма сервером сразу отображать запись со статусом «Загружен» и автоматически ставить её в очередь. Загрузка не должна ожидать завершения OpenAI-запросов. Для принятого файла возвращать `202 Accepted` с идентификатором встречи. Незавершённые и отклонённые загрузки очищать; успешный приём подтверждать только после сохранения оригинала и устойчивой регистрации задания.

### 3.2. Автоматический импорт из локальной папки

Под «внутренней папкой» понимать реальный каталог внутри `MEETING_DATA_DIR`, а не только список в интерфейсе:

`data/incoming/<owner_id>/<project_id>/`

Использовать числовые идентификаторы, а не имена пользователей или проектов. Каталог привязывать только к существующему проекту того же владельца; создавать его при настройке входящих для проекта. В интерфейсе показывать пользователю его путь и краткую инструкцию. Сканер не принимает от клиента произвольные пути.

При работающем приложении сканировать настроенные каталоги раз в 5 секунд; при запуске также проверять накопившиеся файлы. Обрабатывать только непосредственные обычные файлы разрешённых форматов. Не следовать симлинкам, junction/reparse point и путям за пределами каталога данных.

Не обрабатывать незавершённое копирование: дождаться неизменности размера и времени изменения не менее 10 секунд и успешного чтения, затем захватить файл атомарным перемещением в служебную область на том же диске. Файлы с временными расширениями игнорировать. Рекомендованный способ добавления — копирование с временным расширением и переименование после завершения. При обнаружении изменений во время захвата отложить импорт.

После захвата выполнить ту же проверку и постановку в очередь, что и для веб-загрузки. Оригинал переместить в постоянное хранилище; повторное сканирование не должно создавать новую встречу. Невалидный файл переносить в карантин внутри каталога данных, регистрировать безопасную ошибку для владельца и не импортировать бесконечно.

Для импорта из папки название брать из имени файла. Дату по умолчанию устанавливать по времени обнаружения, отмечать её как автоматически установленную; не выдавать её за достоверное время съёмки. Дать владельцу возможность исправить название и дату. Дату из примера или имени файла автоматически не угадывать.

Автоматическое обнаружение действует, пока сервер приложения запущен. Установка Windows-службы в объём работ не входит.

## 4. Автоматический конвейер

Последовательность обработки принятого видео:

1. Зафиксировать владельца, проект, оригинальный файл, метаданные и задание в SQLite.
2. Фоновым исполнителем атомарно захватить задание и установить «Обрабатывается».
3. Извлечь звуковую дорожку локально, без отправки видео сторонним сервисам. Сохранить неизменённый оригинал видео; извлечённое аудио для воспроизведения сохранять без потерь, если технически возможно, иначе документировать используемое преобразование.
4. Передать аудио в существующую границу Speech-to-Text в `ai.py`. При необходимости создать отдельный временный сжатый файл с учётом действующего лимита сервиса.
5. Полученные реальные сегменты держать только в памяти и передать в существующий анализ вместе с названием, датой, проектом и профилем владельца.
6. Проверить структуру ответа и правила личных поручений.
7. Одной транзакцией сохранить итог, синхронизировать личные задачи и установить «Готов».
8. Удалить из памяти сегменты и очистить временные файлы при любом исходе. Оригинальная запись и аудио для воспроизведения остаются.
9. Обновить данные в открытом интерфейсе без перезагрузки страницы.

Не выполнять тяжёлое декодирование и синхронные OpenAI-запросы в основном цикле обработки HTTP. Для первой версии достаточно одного фонового исполнителя с очередью в SQLite. Очередь только в памяти или один `BackgroundTasks` без восстановления не удовлетворяют ТЗ.

Предусмотреть тайм-ауты декодирования и внешних запросов. Путь к FFmpeg/средству проверки медиа должен определяться явно. Не предполагать, что установленный `imageio-ffmpeg` содержит отдельный `ffprobe`; выбранный способ проверки и необходимые зависимости описать в README. Запускать процессы аргументами без shell и не сохранять необработанный stderr в пользовательских ошибках.

При реализации проверить текущую документацию OpenAI, поддержку выбранной модели, формата ответа и ограничения аудио. Сохранить настройку моделей через окружение. Фиксированное время завершения облачной обработки не гарантировать.

## 5. Требования к результатам AI

Все выводы должны опираться на распознанную речь конкретной записи. Название файла, демонстрационный текст и заранее подготовленные карточки не являются источником фактов о встрече.

| Раздел | Требование |
| --- | --- |
| Краткое содержание | Сжатое связное описание разговора, обычно 2–5 предложений, без последовательного пересказа всего транскрипта |
| Основные темы | Обычно 3–5 ключевых вопросов; если в записи меньше тем, вернуть фактическое количество |
| Принятые решения | Только подтверждённые договорённости; предложение не превращать в принятое решение |
| Задачи | Конкретные действия после встречи, без выдуманных исполнителей и сроков |
| Открытые вопросы | Только вопросы, оставшиеся нерешёнными по содержимому записи |

При отсутствии решений, задач или открытых вопросов возвращать пустой массив; в интерфейсе показывать «Не выявлено». Не дополнять результат ради количества пунктов. Для отсутствующего исполнителя или срока хранить `null`, отображать «Не указан»; не подставлять текущего пользователя и текущую дату.

Имена не выводить из меток `A`, `B` и других идентификаторов говорящих. Таймкоды использовать только при наличии реальных сегментов; проверять их попадание в длительность записи. Относительные сроки рассчитывать только при однозначной дате встречи и формулировке; иначе сохранять исходную формулировку без выдуманной календарной даты.

Тишину и отсутствие распознаваемой речи завершать понятной ошибкой, без создания фиктивного резюме. Невалидный ответ модели, отказ или обрыв ответа не считать успешным анализом. Содержимое записи считать входными данными: произнесённые инструкции не должны менять правила анализа или получать доступ к ключам и другим встречам.

В аналитике показывать все выявленные задачи встречи. В «Мои задачи» автоматически включать только явные поручения владельцу встречи с подтверждённым именем или вариантом упоминания, сохранив существующую дополнительную проверку в `ai.py`.

## 6. Состояния, повторы и восстановление

Для новых записей использовать устойчивые машинные статусы с отображением:

| Код | Текст в интерфейсе | Значение |
| --- | --- | --- |
| `uploaded` | Загружен | Файл сохранён, задание ожидает исполнителя |
| `processing` | Обрабатывается | Выполняется извлечение аудио, распознавание или анализ |
| `ready` | Готов | Валидные результаты и личные задачи сохранены |
| `error` | Ошибка обработки | Требуется исправление причины или повтор |

Для `processing` дополнительно показывать этап: «Извлечение аудио», «Распознавание речи», «Анализ содержания», «Сохранение результатов». Не показывать выдуманные проценты AI-обработки. Существующие статусы ручных встреч привести к отображению совместимым адаптером; старые записи не ставить автоматически в новую очередь.

Добавить «Повторить обработку» для ошибочной записи. Это исключительный сценарий восстановления; первичная обработка всегда автоматическая. Повтор использует сохранённый оригинал, не требует повторной загрузки и не создаёт новую встречу.

На старте приложения автоматически возвращать прерванные задания в очередь через механизм срока владения/lease. Защищать от одновременного захвата двумя исполнителями, повторного запроса запуска и сохранения результата устаревшей попытки. После трёх последовательных прерываний одного задания переводить его в ошибку, чтобы избежать бесконечного цикла. Управлять стартом и остановкой исполнителя через lifespan.

Если сервер остановился после распознавания, повторно извлечь/распознать аудио: транскрипт нельзя сохранять для восстановления. Не обещать строго один внешний запрос при аварии; гарантировать одну встречу и отсутствие дублирующихся личных задач.

Использовать SHA-256 файла и уникальность `(owner_id, project_id, content_hash)` для новых видео: одинаковые байты в том же проекте возвращают существующую запись, включая ошибочную, без повторного запуска. Повтор ошибки запускается явно. Другой владелец или проект не раскрывается и не блокируется. Разные файлы с одинаковым именем принимаются независимо.

При повторном запуске не удалять вручную созданные задачи. Синхронизация ранее импортированных поручений должна сохранять статус и правки существующих задач и не плодить дубли; предусмотреть устойчивую идентичность задач внутри одной встречи, а не только индекс массива AI. Если уже обработанная запись перерабатывается, последний успешный результат сохранять до атомарной записи нового; ошибка повтора не должна его уничтожать.

Удаление встречи, проекта или аккаунта во время обработки должно отменять её либо делать позднюю запись результата невозможной. Фоновые задания не должны восстанавливать удалённые данные.

## 7. Страница «Аналитика встреч»

Добавить отдельный пункт основной навигации. По умолчанию показывать все встречи текущего пользователя с сохранёнными успешными итогами, включая существующие обработанные аудио- и текстовые встречи. Записи в обработке и с ошибкой показывать отдельным блоком текущих состояний. Дать фильтры по проекту и периоду даты встречи.

Верх страницы:

- заголовок и краткая подпись о назначении раздела;
- основной показатель «Обработано встреч» — число уникальных встреч с сохранённым успешным результатом, не число попыток;
- дополнительные счётчики «В обработке» и «Ошибки»;
- кнопка перехода к загрузке во «Входящие записи».

Счётчики и список учитывать только для текущего владельца и выбранных фильтров. При ошибке переработки встреча с предыдущим результатом остаётся в числе обработанных и дополнительно учитывается как ошибка текущей попытки; это пояснить подписью.

Ниже — последние встречи по дате встречи, от новых к старым, по 20 записей на страницу. Карточка содержит название, дату, проект, статус, краткое содержание, основные решения и задачи. Длинные списки сокращать с указанием количества оставшихся пунктов и ссылкой «Подробнее». Непроанализированная запись показывает этап или ошибку вместо результата.

При выборе встречи открывать подробный экран: название и дата, статус, проигрыватель оригинального видео или сохранённого аудио, краткое содержание, темы, решения, все задачи и открытые вопросы. Сохранить доступ к дополнительным существующим разделам результатов. При поддержке браузером видео использовать `<video controls>`; при неподдерживаемом кодеке обеспечить аудиовоспроизведение и скачивание оригинала через защищённый маршрут.

Визуальные требования: светлая спокойная палитра, контрастный основной акцент, хорошо различимые карточки и показатели, читаемая типографика, достаточные отступы. Статусы различать цветом и текстом. Дизайн согласовать с существующим интерфейсом, обеспечить работу на узком экране и управление с клавиатуры.

Предусмотреть пустой список с приглашением загрузить запись, индикаторы первоначальной загрузки, ошибку получения списка с повтором запроса и состояние недоступности сети. Сбой опроса сервера не изменяет сохранённый статус обработки встречи.

Обновлять открытые списки, счётчики и детальный экран опросом раз в 3 секунды при наличии активных заданий. Останавливать опрос при уходе со страницы или выходе из аккаунта, не допускать параллельных одинаковых запросов и подмены данных запоздавшим ответом другой страницы. Новые внешние файлы обнаруживать и при отсутствии уже известных заданий: в активном разделе выполнять фоновое обновление не реже раза в 10 секунд. После перезагрузки брать данные с сервера, а не из демонстрационных объектов или одного localStorage.

## 8. Хранение, API и безопасность

Добавить следующую миграцию (при текущем состоянии — версию 2), сохранив данные версии 1. Учесть, что `meetings.source_type` сейчас ограничен `audio`/`text`: поддержку `video` добавить корректной миграцией SQLite с сохранением связей, индексов и существующих записей.

Предусмотреть метаданные оригинального видео, размер, фактический формат, длительность, хеш, способ поступления, автоматически установленную дату, статус/этап обработки, безопасную ошибку, число попыток и время обработки. Для очереди хранить идентификаторы владельца/встречи, состояние, номер попытки и lease. Транскрипт, сегменты и полные запросы/ответы Speech-to-Text в базе не хранить.

Рекомендуемые маршруты, совместимые с текущими `/api/meetings`:

- `POST /api/incoming` — загрузка одного файла и постановка в очередь; пакетную загрузку интерфейс выполняет отдельными запросами с ограниченной параллельностью;
- `GET /api/incoming` — список и состояния входящих записей владельца;
- `GET /api/analytics` — счётчики и пагинированный список, фильтры проекта и периода;
- `GET /api/meetings/{id}` — существующий детальный маршрут с новыми безопасными метаданными;
- `PATCH /api/meetings/{id}` — изменение названия и даты владельцем; во время обработки отклонять изменение контекста с понятным сообщением;
- `GET /api/meetings/{id}/video` — защищённое воспроизведение/скачивание оригинала;
- `POST /api/meetings/{id}/retry` — повтор после ошибки;
- `GET/PUT /api/projects/{id}/incoming` — получение пути и включение/выключение импорта для собственного проекта.

Итоговую форму контрактов документировать. Для каждого маршрута, включая статистику, фильтры, статус, повтор, медиа и настройку папки, проверять сессию и `owner_id`. Администратор не получает доступ к чужому содержимому. Для изменений использовать существующий CSRF-механизм. Фоновый исполнитель проверяет существование владельца и принадлежность проекта, работает от имени владельца, а не администратора или пользователя последней HTTP-сессии.

Оригиналы хранить под сгенерированными именами внутри каталога данных; клиентское имя использовать только как экранируемые метаданные. Не раздавать каталог данных через статику. Медиа-маршрут должен поддерживать перемотку и корректный Content-Type. Удаление данных должно очищать связанные оригиналы, аудио и служебные файлы без выхода за разрешённые каталоги.

Ключ остаётся на сервере в Windows DPAPI. Не сохранять полный транскрипт, исходный TXT, вставленный текст, ключ, тело внешнего запроса или ответ Speech-to-Text в файлах, логах, ошибках и резервных копиях. Допустимы только сжатые структурированные итоги. Временный аудиофайл для отправки удалить в `finally`, после аварии очищать оставшиеся служебные временные файлы при следующем запуске.

Обновить резервное копирование: включить оригиналы видео, постоянное аудио, настройки папок и принятые/ожидающие обработки входящие файлы; исключить временные производные и карантин. Восстановленная очередь должна повторно запускаться по описанным правилам. Сохранить требование остановки приложения перед резервной копией.

## 9. Понятные ошибки

Показывать безопасную причину и действие: «Поддерживаются WebM и MP4», «Запись должна длиться от 2 до 5 минут», «Размер файла превышает 200 МиБ», «В видео отсутствует звуковая дорожка», «Файл повреждён или кодек не поддерживается», «В записи не обнаружена речь», «Администратору нужно настроить ключ OpenAI», «Нет соединения с сервисом распознавания», «Исчерпана квота или превышен лимит запросов», «Не удалось получить структурированные итоги».

Не показывать пользователю трассировки, локальные служебные пути, ключи и сырой текст исключений внешних библиотек. Ошибка в одном файле не должна блокировать остальные задания. Не выполнять бесконечные платные повторы при ошибке ключа, квоты или формата; дальнейший запуск после устранения причины доступен владельцу кнопкой повтора.

## 10. Приёмка и проверка

Доработка принята, если выполнены следующие сценарии:

1. Валидные MP4 и WebM с речью длительностью 2–5 минут принимаются через интерфейс, без ручного запуска последовательно проходят обработку и появляются в аналитике.
2. Помещение валидного файла в настроенную папку при работающем сервере автоматически создаёт встречу после стабилизации файла; при отсутствии очереди интерфейс также обнаруживает её. После запуска сервера импортируется файл, добавленный во время остановки.
3. Копирование по частям, повтор сканирования, одинаковые байты под другим именем и повтор HTTP-запроса не создают дубликаты встречи в одном проекте.
4. Проверены границы 120/300 секунд, превышение размера, пустой файл, подмена расширения, повреждение, отсутствие звука и неподдерживаемый кодек. Ошибки понятны и видны нужному владельцу.
5. Результаты содержат пять обязательных разделов; названные факты соответствуют речи. Если в записи нет сроков, исполнителей, решений или трёх тем, они не выдумываются.
6. Две разные реальные записи дают результаты по собственному содержанию. Демонстрационная встреча с клиентом не появляется без соответствующей речи.
7. Состояния и результаты сохраняются после обновления страницы и перезапуска сервера. Прерванное задание восстанавливается, два исполнителя не завершают одну попытку дважды, серия аварий ограничена.
8. Ошибка сети, ключа, квоты, декодирования или структуры AI не создаёт успешных результатов. После устранения причины повтор использует оригинал и сохраняет предыдущие успешные итоги до завершения.
9. Все задачи отображаются в итогах; только явные личные поручения попадают в «Мои задачи». Повтор не создаёт дубли и сохраняет пользовательские правки и статусы существующих задач.
10. Пользователь и администратор не могут получить чужие списки, счётчики, состояния, подробности, медиа и задания или запустить чужой повтор/импорт. Проверены CSRF, выход за каталог, reparse point и вредоносное имя файла.
11. После успеха, ошибки и перезапуска нет сохранённого транскрипта в базе, SQLite WAL, временных файлах, логах и сообщениях ошибок. Временные файлы отправки очищены, оригинальные записи доступны для воспроизведения.
12. Удаление встречи или проекта во время работы не восстанавливает данные поздним ответом исполнителя. Резервная копия восстанавливает результаты и оригинальные медиа.
13. Миграция существующей базы сохраняет пользователей, проекты, встречи, связи и задачи. Существующие сценарии аудио/TXT/текста продолжают работать.
14. В интерфейсе проверены пустой список, загрузка, все статусы, ошибка обновления, фильтры, пагинация, детальный экран, перемотка и узкий экран; обновление состояния не требует ручной перезагрузки.

Автоматизированные интеграционные тесты расширить в `tests/test_flow.py` или отдельных модулях. В тестах подменять клиента OpenAI и использовать временные каталоги/базу. Нужны проверки прохождения реальных сегментов через конвейер, валидации схемы и отсутствия утечки исходного текста; реальные ключи и платные API-запросы в тестах запрещены. Проверку смыслового соответствия провести отдельно на реальных записях с настроенным ключом; если она не выполнена, явно указать это в отчёте, не считать подмену клиента доказательством качества AI.

Обязательные команды после изменения кода:

```powershell
python -m pytest -q
node --check meeting_app/static/app.js
```

Ручной сервер запускать только на `127.0.0.1` по README. Обновить README: установка медиа-зависимостей, лимиты, папки импорта, автоматический запуск, восстановление и повторы, отсутствие сохранённого транскрипта, резервное копирование.
